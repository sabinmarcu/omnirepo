# Website Models Usage Breakdown

## Scope

This note documents model behavior and runtime usage for the website app models in [apps/website/models](apps/website/models).

## Model Hierarchy

- Base: [Resource.ts](apps/website/models/Resource.ts)
- Source parser: [SourceResource.ts](apps/website/models/SourceResource.ts) extends Resource
- MDX parser: [GenericMdxResource.ts](apps/website/models/GenericMdxResource.ts) extends Resource
- MDX convenience layer: [MdxResource.ts](apps/website/models/MdxResource.ts) extends GenericMdxResource
- Showcase composition layer: [ShowcaseResource.ts](apps/website/models/ShowcaseResource.ts) extends MdxResource
- Domain specializations:
  - [ToolResource.ts](apps/website/models/ToolResource.ts) extends ShowcaseResource
  - [SnippetResource.ts](apps/website/models/SnippetResource.ts) extends ShowcaseResource
- Shared schemas: [schemas.ts](apps/website/models/schemas.ts)

## Derived Inheritance Hierarchy And Intent

The hierarchy is intentionally layered from generic file handling to domain-specific website content.

1. [Resource.ts](apps/website/models/Resource.ts)
- Generic lifecycle and caching shell for any resource input.
- Defines the common flow all other resources rely on.

2. [GenericMdxResource.ts](apps/website/models/GenericMdxResource.ts)
- Adds MDX parsing and metadata/content schema validation on top of Resource.
- Keeps MDX parsing reusable without committing to website-specific directory conventions.

3. [MdxResource.ts](apps/website/models/MdxResource.ts)
- Adds MDX directory discovery behavior and slug-based convenience APIs.
- Bridges generic MDX parsing to route-friendly operations.

4. [ShowcaseResource.ts](apps/website/models/ShowcaseResource.ts)
- Specializes MdxResource for showcase-style pages (preview + showcase + optional overview).
- Translates MDX annotations into concrete SourceResource instances.

5. [ToolResource.ts](apps/website/models/ToolResource.ts)
- Domain binding for the tools section via resourceDirectory = tools.

6. [SnippetResource.ts](apps/website/models/SnippetResource.ts)
- Domain binding for snippets plus subpage source file collections.
- Adds snippet-specific helpers such as getPage and subpages.

Parallel specialization branch:

- [SourceResource.ts](apps/website/models/SourceResource.ts) extends [Resource.ts](apps/website/models/Resource.ts) directly.
- This is separate from the MDX chain because source files need code parsing, language metadata, region grouping, and TOC generation from parsed code blocks.

## Why This Structure Exists

This structure exists to separate concerns by content abstraction level and to minimize duplication across website sections.

1. One lifecycle, many resource types
- Resource centralizes loading lifecycle and cache behavior so all derived models share consistent read and parse semantics.

2. Reuse between section-level MDX and showcase pages
- GenericMdxResource and MdxResource provide reusable MDX parsing for both section metadata pages and content collections.

3. Composition over duplicated route logic
- ShowcaseResource captures a recurring page shape used in both tools and snippets, avoiding repeated preview/showcase/overview assembly logic.

4. Domain adapters for route semantics
- ToolResource and SnippetResource adapt the same base composition to each section directory and routing pattern.

5. Dedicated source parsing path
- SourceResource handles code-focused concerns that are orthogonal to MDX concerns, keeping the MDX model chain clean.

6. Strong schema boundaries
- schemas.ts plus per-resource schema extension enforce content contracts and reduce runtime surprises in route rendering.

7. Route ergonomics and SSG/metadata support
- slugs, fromSlug, getList, and toc/title getters are shaped for Next route generation, metadata APIs, and navigation building.

## Runtime Flow

1. Route/layout loads resource via static model API:
- getList()
- from(pathOrImport, options)
- fromSlug(slug)

2. Resource lifecycle (base class):
- constructor(pathOrImport)
- prepareRead(options)
- readFile()
- prepareParse(options)
- parse()

3. Parsed outputs are consumed by pages/components:
- title, slug, toc
- showcase preview/content component exports
- parsed source sections for subpages

## Per-Model Behavior

## Resource

Defined in [Resource.ts](apps/website/models/Resource.ts).

Responsibilities:

- Generic lifecycle orchestration for all derived models.
- Supports input as file path string, imported module object/promise, or ReactNode payload.
- Provides list loading with resourceDirectory + optional resourceFilter.
- Provides instance creation via static from and static getList.

Key behavior notes:

- readFile for string input stores a normalized path-like value in rawContent.
- Relative path strings are rejected unless subclass sets acceptsRelativePaths = true.
- Static caches exist for string keys and non-string import keys.

Important implementation detail:

- from computes cacheKey via prepareCache, but has/set/get currently use pathOrImport directly instead of cacheKey. This means cache busting logic in subclasses (for example SourceResource.prepareCache) is not fully applied in current implementation.

## GenericMdxResource

Defined in [GenericMdxResource.ts](apps/website/models/GenericMdxResource.ts).

Responsibilities:

- Parse MDX-like module content into:
  - metadata validated by metadataSchema + tocSchema
  - codehike-transformed body validated by contentSchema

Inputs/outputs:

- Input can be import('./content.mdx') or string path.
- parse() uses readRawContent and codehike parse.
- Exposes protected metadata/codehikeContent for subclasses.

## MdxResource

Defined in [MdxResource.ts](apps/website/models/MdxResource.ts).

Responsibilities:

- Adds mdx resource filtering (.mdx only) for directory scans.
- Adds slug-centric APIs:
  - slugs
  - fromSlug
- Adds public getters:
  - title
  - slug
  - content
  - toc

Usage:

- Section layout metadata pages load static MDX with:
  - [app/tools/layout.tsx](apps/website/app/tools/layout.tsx)
  - [app/snippets/layout.tsx](apps/website/app/snippets/layout.tsx)

## SourceResource

Defined in [SourceResource.ts](apps/website/models/SourceResource.ts).

Responsibilities:

- Parse source files/modules into renderable structured sections.
- Metadata model for title/slug/lang with fallbacks.
- Optional path prefixing for relative paths.
- TOC generation from parsed section titles.

Internal pipeline:

- readRawContent when needed from [readRawContent.ts](apps/website/content/readRawContent.ts)
- parseSourceFile from [parseSource.ts](apps/website/data/parseSource.ts)
- TOC tree conversion with [utils/toc.ts](apps/website/utils/toc.ts)

Output shape is later rendered in snippet subpages (headings, comments, code blocks).

## ShowcaseResource

Defined in [ShowcaseResource.ts](apps/website/models/ShowcaseResource.ts).

Responsibilities:

- Parse a showcase MDX document with required codehike annotations:
  - showcase (required)
  - preview (optional)
  - children (overview pointer)
- Materialize 3 linked SourceResource instances:
  - showcase
  - preview (fallback to showcase)
  - overview (optional)

Primary consumer:

- [ShowcaseCard.tsx](apps/website/components/ShowcaseCard.tsx) uses preview.Component + title + slug.

## ToolResource

Defined in [ToolResource.ts](apps/website/models/ToolResource.ts).

Responsibilities:

- Minimal specialization of ShowcaseResource with resourceDirectory = tools.

Route usage:

- tools listing uses getList: [app/tools/page.tsx](apps/website/app/tools/page.tsx)
- tool detail routes use slugs/fromSlug:
  - [app/tools/[slug]/page.tsx](apps/website/app/tools/[slug]/page.tsx)
  - [app/tools/[slug]/layout.tsx](apps/website/app/tools/[slug]/layout.tsx)

## SnippetResource

Defined in [SnippetResource.ts](apps/website/models/SnippetResource.ts).

Responsibilities:

- Extends ShowcaseResource schema with file[] annotations.
- Converts each file entry into SourceResource instances.
- Builds files collection as:
  - showcase
  - overview
  - all declared file sources
- Exposes helpers:
  - getPage(slug)
  - subpages

Route usage:

- snippets listing: [app/snippets/page.tsx](apps/website/app/snippets/page.tsx)
- snippet detail: [app/snippets/[slug]/page.tsx](apps/website/app/snippets/[slug]/page.tsx)
- snippet shell nav built from snippet.files: [app/snippets/[slug]/layout.tsx](apps/website/app/snippets/[slug]/layout.tsx)
- snippet subpage rendering and toc:
  - [app/snippets/[slug]/[subpage]/page.tsx](apps/website/app/snippets/[slug]/[subpage]/page.tsx)
  - [app/snippets/[slug]/[subpage]/layout.tsx](apps/website/app/snippets/[slug]/[subpage]/layout.tsx)

## Shared Schemas

Defined in [schemas.ts](apps/website/models/schemas.ts).

- metadataSchema:
  - title
  - optional slug
- tocSchema:
  - recursive toc node structure used by layout components

TOC consumers:

- [layouts/TOCLayout.toc.tsx](apps/website/layouts/TOCLayout.toc.tsx)
- [utils/toc.ts](apps/website/utils/toc.ts)

## How Models Are Used In Practice

- Navigation and static params are model-driven (slugs/fromSlug/getList).
- Content rendering is model-driven:
  - Showcase pages render component exports from parsed source modules.
  - Snippet subpages render parsed source groups with section comments/variants.
- Metadata generation is model-driven (title/toc/slug from resource instances).

## Next-Step Notes

1. If adding a new content type under tools/snippets, prefer extending ShowcaseResource or MdxResource to preserve route conventions.
2. If adding cache-busting semantics, fix Resource.from cache key usage to use cacheKey consistently for has/get/set.
3. Keep model outputs serializable or render-safe for server components, especially Component payloads from SourceResource.
4. Keep toc/title/slug contract stable because route metadata, side navigation, and TOC layouts depend on it.
5. Re-enable or implement generateStaticParams blocks after confirming model scanning cost and cache behavior in production.
